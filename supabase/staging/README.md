# Building staging

Staging is Supabase project `yuvkaewmxqdslvigdsrp`, in a **separate free
organisation**. The Supabase connection used for production cannot see that
organisation, so the schema cannot be pushed to it — it has to be pasted into
that project's SQL editor once. The `.sql` files here are what to paste.

Generated by `scripts/build-staging-schema.py`. **Do not edit them by hand** —
change the generator and re-run it, or the next regeneration silently discards
the edit.

```bash
python3 scripts/build-staging-schema.py
```

## The procedure

1. Open the **staging** project's SQL editor. Check the project ref in the URL
   before you paste anything. Production is `rxtlnetlzmbqirqaalkw`; this must
   not be that.
2. Paste `01_of_07.sql` in full, run it, wait for it to finish.
3. Repeat for `02` through `07`, **in order**.
4. Run `98_verify.sql`. Every row must say `OK`.

## If a chunk fails

**Do not re-run it.** The Supabase SQL editor does not honour an outer
`begin`, so a script that fails half way through has already applied
everything before the failure — a blind re-run then fails on the first object
that already exists, which looks like a different problem and is not.

Run `99_resume.sql` instead. It reports how many migrations landed and which
was last, because every migration stamps itself into
`supabase_migrations.schema_migrations` as it goes. Match `last_applied`
against the `-- nn/71 <filename>` headers in the chunks and carry on from the
next one, deleting from the chunk file the migrations that already applied.

## What the generator does that a plain concatenation does not

**Inserts one `drop function`.** `promotion_summaries` widens its return type
with `create or replace`, which Postgres refuses (42P13), and unlike the other
four functions that widen theirs it does not drop itself first. Without that
line the replay stops dead at migration 52 of 71.

`supabase/README.md` names two outstanding cases. That is stale — the
`generate_routes` workaround it describes is already in the migration file.
The check that matters is not whether the return type changed but whether a
drop precedes the redefinition in the same file.

**Records the migration history.** Each migration stamps its version and name,
so staging ends up with the same 71 rows production has. Without this a later
`supabase db push` would try to replay all 71 against a database that already
has them.

**Cuts on migration boundaries**, so a chunk never fails part way through a
statement, and the stamp tells you exactly where it stopped.

## What this does not do

It creates the **schema only**. No products, stores, routes, form templates,
accounts or storage objects. Staging starts empty, which is the point — it is
for testing changes, not for holding a copy of the business.

It does not create the storage **objects**, only the buckets and their
policies.

Rep and manager accounts for staging have to be created in that project's
auth, and each needs a `profiles` row written by hand: there is **no trigger**
on `auth.users`, and `org_id` and `role` have no defaults, so an auth user
with no profile row can sign in and then see nothing.
